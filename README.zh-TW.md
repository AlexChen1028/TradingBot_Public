# 加密貨幣期貨交易機器人（節錄展示）

> English version: [README.md](README.md)

一個 24/7 運行的加密貨幣期貨交易機器人，結合了多重技術訊號堆疊的進場邏輯，
以及一套把 YouTube 市場評論轉成可機器讀取風控參數的資料管線，跑在 Binance
USDⓈ-M 永續合約上。這是一個更大、私有運作系統的**節錄版本**；這裡收錄兩份
有代表性的程式碼，而不是完整的正式檔案（主程式約 4,700 行、累積五個月的
事故應對紀錄）——原因見文末[說明](#說明)。

## 這份節錄展示了什麼

- 用多重訊號堆疊的進場過濾機制，而不是單一指標決定進出場
- 一條不太常見的資料管線：RSS 偵測新影片 → 逐字稿擷取（原生字幕優先，
  字幕關閉的頻道退而求其次跑本機 Whisper 語音辨識）→ 結構化的市場判斷
  登記簿，餵給真正的風控參數
- 三則具體的「事故 → 修法 → 回歸測試」故事，而不是一個把除錯過程全部
  抹掉、只剩成品的系統
- 一篇對自己回測方法論的自我批判文件，包含早期版本為什麼不能被信任的
  七個具體原因
- 在一個原本沒有測試框架的程式碼庫裡，用依賴注入寫出可測試、有單元測試
  覆蓋的風控工程程式碼——因為真正撞過真實事故的那一塊，正是最值得被
  釘死行為的那一塊

### 1. 進場靠的是多重過濾堆疊，不是單一訊號

一次掃描會產出一個訊號計數（量能異常放大、壓縮盤整、逼近突破位、資金費率
異常），需要好幾個同時成立才會被列入候選。在這之上還疊了一層彼此獨立的
否決條件：RSI 極端值、趨勢方向是否一致、一個全域方向性偏向開關、是否貼近
已知的支撐/壓力帶、幣種黑名單、以及一個每小時投票一次的總經氛圍判斷。
單獨看每一項都不複雜；真正的紀律在於**絕不讓任何一項單獨授權一筆交易**，
而且每一道否決條件的命中率都要定期稽核——這樣一道悄悄失效（或悄悄變成
永遠擋掉某個方向）的過濾器，才不會是靠運氣才被發現的。

### 2. 風控參數來自一條文字管線，不只是回測調出來的（`kol_fetch.py`）

這是真的能跑的程式碼範例。三個 YouTube 頻道幾乎每天都會發布加密貨幣市場
分析；`kol_fetch.py` 定期輪詢它們的 RSS 訂閱，對每一支新影片抓逐字稿——
優先用原生字幕，字幕關閉的頻道則退而求其次跑一次本機 Whisper 語音辨識——
再把原始文字交給後續的結構化擷取流程，寫進一份有版本紀錄的價位/理由登記簿。
程式碼裡幾個值得一提的細節：

- **頻道 ID 是寫死的，不是每次執行都重新爬網頁解析**——早期版本每次都重新
  爬 `youtube.com/@handle`，偶爾會被限流導致誤判「找不到頻道」，而這個
  誤判和「真的沒有新片」在下游看起來完全一樣。
- **真的沒有語音的影片（純推廣短片、純音樂）會立刻被標記為退休**，
  和「轉錄暫時失敗、之後可能會成功」的情況分開處理，後者才會在
  `RETIRE_HOURS` 之內持續重試。沒有這個區分之前，一支沒有語音的短片
  會被無限期地每輪重新下載、重新跑一次 Whisper 模型。
- **每一筆退休紀錄都連同標題一起落檔**，不是只留一個影片 ID——這樣「這個
  判斷是不是對的」這件事，事後永遠可以被回頭檢查，而不是一個沒有留下
  任何線索、無法覆核的永久決定。

### 3. 一次事故、一個修法、以及修法本身的測試（`fast_direction_watch.py`）

如果只能看一個檔案，我會推薦這個。機器人使用 `closePosition=True` 的
條件單來做止損/止盈。調查一連串來路不明的反向倉位時，發現了一個真實
存在的交易所端怪異行為：在某個幣種上，這類條件單觸發時大約有一半機率會
**超額成交**——把原本要平的倉位平掉之後，直接反向開出一個等額的新倉位，
而且完全沒有掛止損。機器人的主迴圈原本每 15 分鐘才掃描一次，代表一個
裸奔、方向錯誤的倉位可能有將近 15 分鐘完全沒有保護；三次真實事故實測的
偵測延遲分別是 2.6、9.5、12.5 分鐘。

這個修法**沒有新增任何下單邏輯**——只是把一個本來就存在的檢查（「本地
記錄的方向是否還跟交易所一致」）從每次掃描一次，改成每 60 秒一次，而且
規定「疑似不符」必須在 3 秒後的第二次讀取仍然一致才會真的觸發接管（否則
查得更頻繁只會把一點點誤判率放大 15 倍）。`test_fast_direction_watch.py`
釘死了 16 個情境——確認一致的不符、會自己恢復的暫時性不符、交易所查詢
直接失敗、偵測器內部丟出例外不得讓主迴圈跟著掛掉——完全不需要連網路、
也不需要真的睡眠等待，而這是一個原本沒有任何測試框架的程式碼庫。

```bash
python test_fast_direction_watch.py
#  16/16 scenarios passed
```

### 4. 第二次事故，這次是因為查錯了地方（`check_algo_protection.py`）

這個專案的文件長年寫著一個「已確認的事實」：模擬（demo）交易環境的 API
看不到、也撤不掉條件單（止損/止盈單）。調查第三次發生的反向倉位事故時，
才找到真正的原因：Binance 早就把條件單搬到一個獨立的「Algo」訂單服務。
機器人原本查詢單子狀態用的是舊版端點，對 Algo 單一律回答「查無此單」
——不是因為單子真的不存在，而是**查錯了端點**。換成正確的參數去查，
同一張單子立刻就查得到，狀態和觸發價都正確。一個被當成「demo 環境
缺陷」寫進文件、掛了好幾個月的說法，其實是自己程式碼裡的查詢錯誤。

`check_algo_protection.py` 就是為了回應這件事而寫的唯讀稽核工具：檢查
每一筆持倉在交易所端是不是真的有一張存活、價位合理的止損單，並且另外
持續追蹤兩種交易所端的失敗模式——單子觸發後超額成交變成反向倉位（如上），
以及單子被觸發卻被交易所直接拒絕，讓倉位短暫失去保護。它刻意**不去改動**
下單邏輯本身——這個專案累積下來的教訓是：事故當下去動下單路徑，往往是
把事故變大、而不是變小的做法。真正要改，得先過一個預先寫好的、可證偽的
觸發條件（見程式內的說明文件）——先把數字量出來，才有資格根據量出來的
結果採取行動。

```bash
python check_algo_protection.py --selftest
#  20/20 scenarios passed
```

### 5. 不裝出一個假的安心感（`stale_gate_report.py`）

一個比較小、但真實發生過的故事。完整的稽核套件會回報哪些交易閘門已經陳舊
——支撐/壓力位不再有任何現行市場判斷支撐、方向性偏向悄悄開始擋掉某一個
方向的所有單子。早期版本的回報層不分青紅皂白，每一行都印一個綠色勾勾。
問題是：稽核用到的其中一份資料只存在於正式環境的容器裡，開發機上永遠讀
不到——於是在開發機上，「這項沒有被檢查」跟「這項檢查過而且沒問題」印出
來是同一個綠色勾勾。有一段時間，整條稽核路徑其實悄悄地沒在跑，而畫面上
完全沒有任何異狀。

修法就是這個檔案裡的三態區分：**有問題**（離開碼 1）、**查不到**
（離開碼 2——這是獨立的一個狀態，不是退回「沒問題」）、以及**真的健康**
（離開碼 0，也是唯一一個 `--quiet` 有權讓它閉嘴的狀態）。這是一個很小的
函式，但它是唯一一個能保證「全部乾淨」的報告跟「我們根本不知道」的報告
絕對不會長得一樣的地方。

```bash
python stale_gate_report.py
#  8/8 scenarios passed
```

## 回測能告訴你什麼、不能告訴你什麼

[`BACKTESTING.md`](BACKTESTING.md) 是私有 repo 內部文件的節錄改寫版，內容
是為什麼一支早期的探索性回測**無法驗證**實盤策略——七個具體的方法論問題
（幣種池的倖存者偏誤、手續費算式裡沒有槓桿、沒有未來函數但在經濟意義上
沒有價值的出場邏輯，還有更多），以及一個真正有效的回測需要什麼。收錄它
是因為這段推理過程比一個報酬率數字有用得多——這也是為什麼不管在這裡還是
原始文件裡，都不會出現那個數字。

## 風控框架（結構說明，非目前即時參數）

| 機制 | 做法 |
|---|---|
| 倉位大小 | 依訊號強度計數縮放，同時受單筆保證金上限限制 |
| 止損／止盈 | 交易所端條件單（`closePosition=True`），每次掃描都會對照交易所實際狀態做核對 |
| 對帳 | 本地持倉記錄與交易所真實狀態的核對：主流幣每 60 秒一次、全部幣種每次掃描一次（見上方事故故事） |
| 相關性控管 | 高度相關資產的同向倉位會被限縮，不會被當成互相獨立的機會分別加碼 |
| 可稽核性 | 每一道可能擋單的過濾條件都會定期被統計命中率——一道悄悄失效、或悄悄擋掉某個方向 100% 訂單的過濾器，會被機制自動抓出來，而不是靠人碰巧發現 |

實際的數值門檻（槓桿倍數、確切的止損百分比、KOL 管線目前登記的支撐/
壓力位）刻意沒有原封不動收錄在這裡——那些每天都在變，也不是這份節錄
真正想呈現的工程內容；產生並稽核這些數字的機制本身才是。

## 技術棧

`Python` · `ccxt`（交易所串接） · `feedparser`（RSS 訂閱） ·
`youtube_transcript_api` + 本機 Whisper 語音辨識備援（逐字稿擷取） ·
依賴注入式單元測試（沒有用測試框架——純函式加 assert）
